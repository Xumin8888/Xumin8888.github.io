## 前言

前端安全是前端面试中经常被问到的话题，也是实际开发中必须重视的问题。随着 Web 应用越来越复杂，前端安全问题也越来越突出。本文将全面讲解前端面试中常见的安全问题，包括 XSS、CSRF、CSP、点击劫持、SQL 注入等多个方面。

掌握前端安全知识，不仅能应对面试，更能在实际项目中写出更安全的代码，保护用户数据和网站安全。

---

## 一、XSS 跨站脚本攻击

### 1. 什么是 XSS？

XSS（Cross-Site Scripting，跨站脚本攻击）是一种代码注入攻击，攻击者通过在网页中注入恶意脚本，使得用户访问页面时执行这些恶意代码。

**为什么叫 XSS 而不是 CSS？**
- 因为 CSS 已经是层叠样式表（Cascading Style Sheets）的缩写了
- 为了避免混淆，所以用 XSS 表示

**XSS 的危害：**
- 窃取用户 Cookie、Session
- 劫持用户账号
- 伪造页面，诱导用户输入敏感信息
- 发送恶意请求
- 控制用户浏览器进行挖矿等操作
- 传播蠕虫病毒

### 2. XSS 的类型

**1. 反射型 XSS（非持久型）**
- 恶意脚本通过 URL 参数传递
- 服务器将恶意代码拼接到 HTML 中返回
- 需要诱导用户点击恶意链接
- 一次性，不持久化

**示例：**
```
http://example.com/search?q=<script>alert(document.cookie)</script>
```

**2. 存储型 XSS（持久型）**
- 恶意脚本被存储到服务器数据库中
- 所有访问该页面的用户都会执行恶意代码
- 危害更大，影响范围更广
- 常见于评论、留言、发帖等功能

**示例：**
用户在评论区输入 `<script>stealCookie()</script>`，这条评论被保存到数据库，所有查看评论的用户都会执行这段脚本。

**3. DOM 型 XSS**
- 不经过服务器，完全在前端发生
- 前端 JS 直接将用户输入插入到 DOM 中
- 不需要服务器参与
- 属于前端自身的安全问题

**示例：**
```javascript
// 危险代码
const urlParams = new URLSearchParams(window.location.search)
const name = urlParams.get('name')
document.getElementById('greeting').innerHTML = '你好, ' + name
```

如果用户访问 `http://example.com/?name=<img src=x onerror=alert(1)>`，就会触发 XSS。

### 3. XSS 防御手段

**1. 输入过滤和验证**
- 对用户输入进行过滤，移除或转义危险字符
- 白名单过滤，只允许合法的标签和属性
- 输入验证，检查输入格式是否符合要求

**2. 输出转义**
- 在将数据插入到 HTML 之前进行转义
- HTML 转义：将 `<`、`>`、`"`、`'`、`&` 等特殊字符转义

```javascript
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;')
}
```

**3. 使用安全的 API**
- 优先使用 `textContent` 而不是 `innerHTML`
- 使用 `setAttribute` 设置属性
- 避免使用 `eval()`、`new Function()` 等执行字符串的方法
- 避免使用 `document.write()`

**4. CSP（内容安全策略）**
- 设置 Content-Security-Policy 响应头
- 限制资源加载来源
- 禁止内联脚本和 eval
- 报告违规行为

**5. HttpOnly Cookie**
- 给 Cookie 设置 HttpOnly 属性
- 防止 JS 读取 Cookie
- 即使 XSS 成功，也偷不到 Cookie

**6. 其他措施**
- 使用安全的框架（Vue、React 等默认会转义）
- 输入长度限制
- 验证码（防止自动化攻击）
- 定期扫描和安全审计

## 二、CSRF 跨站请求伪造

### 1. 什么是 CSRF？

CSRF（Cross-Site Request Forgery，跨站请求伪造）是一种挟制用户在当前已登录的 Web 应用上执行非本意的操作的攻击方法。

**CSRF 的原理：**
1. 用户登录了 A 网站，浏览器保存了 A 网站的 Cookie
2. 用户在没有退出 A 网站的情况下，访问了恶意网站 B
3. 恶意网站 B 向 A 网站发送请求
4. 浏览器会自动带上 A 网站的 Cookie
5. A 网站误以为是用户本人操作，执行了请求

**CSRF 的危害：**
- 以用户名义发送邮件、发消息
- 盗取用户账号
- 购买商品、转账
- 修改用户信息
- 删除数据

### 2. CSRF 的特点

- 攻击发生在第三方网站
- 利用用户的登录状态（Cookie）
- 攻击者只知道请求的参数，看不到响应
- 可以伪造 GET 和 POST 请求
- 是跨站的请求

### 3. CSRF 防御手段

**1. 验证 Referer 头**
- 检查请求的 Referer 是否来自本站
- 简单易实现，但不够安全
- Referer 可以被篡改或禁用

```javascript
// 简单的 Referer 验证
function checkReferer(req) {
  const referer = req.headers.referer
  return referer && referer.startsWith('https://example.com')
}
```

**2. CSRF Token**
- 服务器生成随机 token，存在用户 session 中
- 前端请求时带上这个 token
- 服务器验证 token 是否正确
- 攻击者拿不到 token，所以无法伪造

**实现方式：**
- 把 token 放在表单 hidden 字段中
- 放在请求头中（如 X-CSRF-Token）
- 放在 URL 参数中（不推荐）

```javascript
// 前端示例
fetch('/api/transfer', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'X-CSRF-Token': csrfToken
  },
  body: JSON.stringify({ amount: 1000 })
})
```

**3. SameSite Cookie**
- 给 Cookie 设置 SameSite 属性
- 限制第三方网站请求时是否携带 Cookie
- 有三个值：Strict、Lax、None

```
Set-Cookie: sessionId=xxx; SameSite=Strict; Secure; HttpOnly
```

- **Strict**：最严格，完全禁止第三方 Cookie
- **Lax**：宽松一些，允许部分第三方请求携带（链接、GET 表单）
- **None**：无限制，但必须同时设置 Secure

**4. 验证码**
- 关键操作需要输入验证码
- 增加攻击难度
- 用户体验稍差

**5. 二次验证**
- 重要操作（转账、修改密码等）需要再次验证身份
- 比如输入密码、手机验证码等

**6. 其他措施**
- 重要操作使用 POST 而不是 GET
- 操作成功后及时清除敏感 Cookie
- 定期重新认证敏感操作

## 三、CSP 内容安全策略

### 1. 什么是 CSP？

CSP（Content Security Policy，内容安全策略）是一个额外的安全层，用于检测并削弱某些特定类型的攻击，包括 XSS 和数据注入攻击等。

**CSP 的作用：**
- 限制资源加载来源
- 禁止内联脚本执行
- 禁止 eval 等动态代码执行
- 报告违规行为
- 有效防御 XSS 攻击

### 2. CSP 的使用方式

**1. HTTP 响应头**
```
Content-Security-Policy: policy
```

**2. meta 标签**
```html
<meta http-equiv="Content-Security-Policy" content="policy">
```

### 3. CSP 常用指令

| 指令 | 说明 |
|------|------|
| default-src | 默认策略，其他指令未指定时使用 |
| script-src | 脚本来源 |
| style-src | 样式来源 |
| img-src | 图片来源 |
| font-src | 字体来源 |
| connect-src | Ajax、WebSocket 等连接来源 |
| frame-src | iframe 来源 |
| media-src | 媒体资源来源（audio、video） |
| object-src | 插件来源（flash 等） |
| base-uri | base 标签的 href 限制 |
| form-action | form 表单提交地址限制 |
| frame-ancestors | 可以嵌入当前页面的父页面 |
| report-uri | 违规报告地址 |

### 4. CSP 常用值

- `'self'`：同源（相同协议、域名、端口）
- `'none'`：不允许任何来源
- `'unsafe-inline'`：允许内联脚本和样式
- `'unsafe-eval'`：允许 eval 等动态代码执行
- `'nonce-xxx'`：允许特定 nonce 的内联脚本
- `'sha256-xxx'`：允许特定哈希值的脚本
- 具体的域名或路径
- 通配符 `*`：允许任何来源

### 5. CSP 示例

**严格模式（防御 XSS 效果最好）：**
```
Content-Security-Policy: 
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' data:;
  font-src 'self';
  connect-src 'self';
  frame-ancestors 'none';
  form-action 'self';
  base-uri 'self';
```

**允许 CDN：**
```
Content-Security-Policy: 
  default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' https://cdn.example.com;
  img-src 'self' https://img.example.com;
```

**报告模式（只报告不拦截，用于测试）：**
```
Content-Security-Policy-Report-Only: 
  default-src 'self';
  report-uri /csp-report
```

### 6. CSP 注意事项

- 开启 CSP 前先在报告模式下测试
- 逐步收紧策略，不要一步到位
- 内联脚本尽量移到外部文件
- 避免使用 eval、new Function 等
- 合理使用 nonce 或 hash 处理必要的内联脚本

## 四、点击劫持

### 1. 什么是点击劫持？

点击劫持（Clickjacking）是一种视觉上的欺骗手段，攻击者通过将目标网站嵌入到自己的页面中，使用透明的 iframe 覆盖在页面上，诱导用户点击看似正常的按钮，实际上点击的是被隐藏的目标网站上的按钮。

**点击劫持的原理：**
1. 攻击者创建一个页面，上面有一个诱人的按钮（比如"中奖了，点击领取"）
2. 在这个按钮上面覆盖一个透明的 iframe，加载目标网站
3. 调整 iframe 的位置，让目标网站的按钮刚好在诱人按钮的位置
4. 用户以为点击的是诱人按钮，实际上点击的是目标网站的按钮

**点击劫持的危害：**
- 诱导用户点赞、关注、转发
- 诱导用户购买商品、转账
- 诱导用户开启摄像头、麦克风
- 诱导用户下载恶意软件

### 2. 点击劫持防御手段

**1. X-Frame-Options 响应头**
- 设置页面是否可以被 iframe 嵌入
- 有三个值：DENY、SAMEORIGIN、ALLOW-FROM

```
X-Frame-Options: DENY          // 完全不允许被嵌入
X-Frame-Options: SAMEORIGIN    // 只允许同源页面嵌入
X-Frame-Options: ALLOW-FROM https://example.com  // 允许指定域名嵌入
```

**2. CSP frame-ancestors 指令**
- CSP 中的 frame-ancestors 指令
- 比 X-Frame-Options 更灵活
- 可以指定多个域名

```
Content-Security-Policy: frame-ancestors 'self' https://trusted.com
```

**3. JavaScript 防御**
- 检查当前页面是否在顶层窗口
- 如果不是，跳出 iframe

```javascript
if (top !== window) {
  top.location.href = window.location.href
}
```

但这种方式可以被攻击者通过 `sandbox` 属性绕过。

**4. 其他措施**
- 重要操作增加二次确认
- 使用验证码
- 检测鼠标位置是否异常

## 五、SQL 注入

### 1. 什么是 SQL 注入？

SQL 注入是通过在应用程序的输入中插入恶意的 SQL 语句，从而操纵数据库的攻击方式。

虽然 SQL 注入主要是后端安全问题，但前端也需要了解：
- 前端可以做一些基础的输入验证
- 了解原理有助于理解整体安全体系
- 面试中也经常会问到

**SQL 注入的原理：**
1. 应用程序直接将用户输入拼接到 SQL 语句中
2. 攻击者输入恶意的 SQL 片段
3. 恶意 SQL 被执行，导致数据泄露或破坏

**示例：**
```javascript
// 危险代码：直接拼接 SQL
const sql = `SELECT * FROM users WHERE username = '${username}' AND password = '${password}'`
```

如果用户输入 `' OR '1'='1` 作为密码，SQL 就变成了：
```sql
SELECT * FROM users WHERE username = 'admin' AND password = '' OR '1'='1'
```
这样就能绕过密码验证。

### 2. SQL 注入的危害

- 数据泄露：拖库，获取所有用户数据
- 数据篡改：修改、删除数据
- 权限提升：获取管理员权限
- 服务器攻击：通过数据库执行系统命令
- 完全控制服务器

### 3. SQL 注入防御手段

**1. 使用预编译语句（Prepared Statements）**
- 使用参数化查询，而不是字符串拼接
- 最有效的防御手段

```javascript
// 安全代码：参数化查询
const sql = 'SELECT * FROM users WHERE username = ? AND password = ?'
db.query(sql, [username, password])
```

**2. 输入验证和过滤**
- 验证输入格式是否符合预期
- 使用白名单验证
- 过滤危险字符

**3. 最小权限原则**
- 数据库账号只授予必要的权限
- 不要用 root 账号连接数据库
- 不同业务使用不同账号

**4. 错误信息处理**
- 不要把数据库错误信息暴露给前端
- 统一的错误处理
- 日志记录错误，但不返回给用户

**5. 其他措施**
- 使用 ORM 框架（自动参数化）
- Web 应用防火墙（WAF）
- 定期安全审计
- 数据加密存储

## 六、其他前端安全问题

### 1. 中间人攻击（MITM）

**什么是中间人攻击：**
攻击者在通信双方之间插入自己，窃取或篡改通信内容。

**防御手段：**
- 使用 HTTPS（SSL/TLS 加密）
- 证书验证
- HSTS（HTTP Strict Transport Security）
- 避免在公共 WiFi 下进行敏感操作

### 2. 密码安全

**常见问题：**
- 密码明文存储
- 弱密码
- 密码传输不加密

**防御手段：**
- 密码加盐哈希存储（bcrypt、scrypt、Argon2）
- 强制密码强度
- 传输使用 HTTPS
- 定期修改密码
- 双因素认证（2FA）

### 3. 文件上传安全

**常见问题：**
- 上传恶意脚本文件
- 上传病毒、木马
- 路径遍历攻击

**防御手段：**
- 验证文件类型（不仅靠后缀名）
- 限制文件大小
- 重命名文件
- 文件存储在非 web 可访问目录
- 图片可以进行二次渲染
- 独立域名存储上传文件

### 4. URL 跳转安全

**什么是开放重定向：**
应用程序接受用户输入的 URL 进行跳转，攻击者可以构造恶意 URL 诱导用户跳转到钓鱼网站。

**防御手段：**
- 白名单验证跳转域名
- 不直接使用用户输入作为跳转地址
- 跳转前提示用户
- 使用 referer 验证

### 5. localStorage / sessionStorage 安全

**注意事项：**
- 不要存储敏感信息（密码、Token 等）
- XSS 攻击可以窃取存储的数据
- 注意数据过期时间
- 敏感数据优先使用 HttpOnly Cookie

### 6. WebSocket 安全

**常见问题：**
- 身份验证问题
- 跨站 WebSocket 劫持
- 消息注入

**防御手段：**
- 连接时验证身份（Token）
- 验证 Origin 头
- 消息输入验证
- 限制连接频率

## 七、前端安全最佳实践

### 1. 输入输出安全

- **所有用户输入都是不可信的**
- 输入验证（白名单优先）
- 输出转义（根据插入的上下文转义）
- 长度限制
- 类型检查

### 2. Cookie 安全

- 敏感 Cookie 设置 `HttpOnly`
- 设置 `Secure`（只在 HTTPS 下传输）
- 设置 `SameSite`（防御 CSRF）
- 设置合理的过期时间
- 最小化 Cookie 中的信息

### 3. 传输安全

- 全站使用 HTTPS
- 开启 HSTS
- 使用安全的 TLS 配置
- 禁用不安全的协议和算法

### 4. 身份认证安全

- 使用安全的会话管理
- Token 安全存储和传输
- 定期重新认证
- 异常登录检测
- 双因素认证

### 5. 依赖安全

- 定期更新依赖包
- 使用 npm audit 检查漏洞
- 避免使用不知名的第三方库
- 最小化依赖数量
- 锁定依赖版本

### 6. 安全编码习惯

- 不要信任任何客户端验证
- 错误信息不要泄露细节
- 日志记录敏感信息要脱敏
- 代码中不要硬编码密钥
- 定期安全培训和审计

## 八、面试常见问题总结

### 1. XSS 和 CSRF 的区别？

| 特性 | XSS | CSRF |
|------|-----|------|
| 全称 | 跨站脚本攻击 | 跨站请求伪造 |
| 原理 | 注入恶意脚本执行 | 利用用户登录状态伪造请求 |
| 攻击目标 | 用户 | 服务器 |
| 需要登录 | 不一定 | 必须 |
| 注入点 | 网页内容 | 请求 |
| 防御 | 转义、CSP、HttpOnly | Token、SameSite、Referer |

### 2. 前端常见的安全问题有哪些？

- XSS 跨站脚本攻击
- CSRF 跨站请求伪造
- 点击劫持
- SQL 注入
- 中间人攻击
- 密码安全问题
- 文件上传安全
- URL 跳转漏洞
- 依赖包漏洞
- 信息泄露

### 3. 如何防御 XSS？

- 输入过滤和验证
- 输出转义
- 使用安全的 API（textContent 代替 innerHTML）
- CSP 内容安全策略
- HttpOnly Cookie
- 使用成熟的框架（Vue、React 自动转义）

### 4. 如何防御 CSRF？

- CSRF Token
- SameSite Cookie
- 验证 Referer
- 验证码
- 二次验证
- 重要操作使用 POST

### 5. CSP 是什么，有什么作用？

- CSP 是内容安全策略
- 限制资源加载来源
- 禁止内联脚本和 eval
- 报告违规行为
- 主要用来防御 XSS 攻击

## 结语

前端安全是前端开发中不可忽视的重要部分，也是面试中的高频考点。安全无小事，一个小小的漏洞可能会造成巨大的损失。

建议大家在日常开发中养成安全编码的习惯，不要等到出了问题才重视。记住最重要的原则：永远不要信任用户的输入。

希望本文能帮你在面试和工作中更好地应对前端安全问题！
